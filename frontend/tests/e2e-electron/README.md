# E2E suite index (Electron + Playwright)

Run procedure: see CLAUDE.md → "Running E2E tests" (`yarn dev` → stop → `node scripts/run-e2e.mjs electron`).
Business rules these specs guard are documented in [docs/FEATURE_GUIDE.md](../../../docs/FEATURE_GUIDE.md).

**LIRA-123 (verification integrity):** `yarn test:e2e` / `yarn workspace @liratek/frontend
test:e2e` can silently exit 0 with ZERO output on Windows dev machines, in well under a
second, instead of running (or correctly erroring on) anything — reproduced repeatedly from
a fresh shell with a `-g` pattern matching no spec, which Playwright itself always fails
loudly on. Always invoke `node scripts/run-e2e.mjs electron` directly from the repo root —
never through a `yarn` wrapper — for a run you can trust locally. It also enforces a floor
on the reported test count so a run that silently did nothing can't report success. CI is unaffected (Linux
runners; confirmed against real run logs showing genuine spec counts) but was switched to
the same direct invocation anyway, per `.github/workflows/ci.yml`'s comment on that step.

## Execution model

- **One Electron instance + one SQLite DB per worker** (`fixtures.ts`), created fresh at
  worker start, then **accumulating across every spec** that worker runs. Default 1 worker
  (`PWTEST_WORKERS` to override), `fullyParallel: false`, files run **alphabetically**:
  `app.spec.ts` → `lira-056…094` → unnumbered `lira-*` → `recharge.spec.ts`.
- `completeSetup()` runs once per worker: base system **OMT**, all modules on, General
  seeded **USD 500 / LBP 9,000,000** (lira-085 asserts these against the setup checkpoint).
- Every spec sets `retries: 0` — a retry relaunches Electron and loses shared sequential
  state (and would duplicate identity-marker rows, e.g. lira-091-variance).
- Navigation is hash-routing via `navigateTo()` (never reload — it would drop the session).

## Assertion discipline (CLAUDE.md rule 15)

- **Deltas, never absolutes**: snapshot the drawer/ledger/balance/profit immediately
  before the action, assert the delta after.
- **Identity, never position**: match rows by `source_table`+`source_id`, unique client
  name/phone, ticket number, unique cents, or a notes marker — never `getRecent()[0]`
  or `tbody tr.first()`. One action can write multiple rows; `created_at` is
  second-granular.
- When asserting `/audit` UI, bounce `navigateTo("/")` → `navigateTo("/audit")` to force
  a fresh mount (a parked viewer shows a stale list).
- Guard tests must be proven to FAIL on the pre-fix code (rule 17).

## Known couplings & hazards

- `lira-alfa-gift-recording` documents that lira-064 leaves a session open; it (and
  `lira-session-multiple-per-day`) close all sessions in `afterEach`. The other session
  specs leave their sessions open — any new spec sensitive to an active session must
  start with `closeAllActiveSessions`.
- Fixed phone numbers are shared across specs (`03999222`, `03999333`, …) — safe only
  because assertions are delta/identity based. Prefer `Date.now()`-unique identities.
- Two files share the `091` number (checkpoint variance, loto ledger sign) — unrelated
  topics; ticket-number collision only. Same for `089` (recharge catalog card
  labels vs. bill commission-at-settlement) — "bill-commission-settlement" sorts
  after the bare "089" alphabetically ("b" < "c" also puts it before
  `lira-089-card-face-values`), so it runs before lira-095's own bill specs.
- Renaming spec files changes alphabetical execution order. The suite is designed to be
  order-tolerant (deltas + identity), but session leakage (above) is the exception —
  verify a full run after any rename.
- `lira-142-exchange-lot-settlement` is the FIRST (and, as of this writing,
  only) spec in the whole suite to create a EUR-denominated
  `exchange_transactions`/`exchange_lots` row (grepped — no other spec ever
  passes `EUR` as `fromCurrency`/`toCurrency` or edits the EUR row in
  `rates`). It ends with the BUY's lot back in an OPEN state at its full
  217 EUR (the SELL is voided; the BUY is intentionally left unvoided since
  voiding it isn't part of the scenario) — harmless to every later spec
  since none of them read EUR positions/lots, but a FUTURE EUR-touching spec
  inherits this open 217 EUR position as its starting point, not zero.
  It also self-provisions `currencies.EUR.is_active = 1` via
  `currencies:update` before touching the UI — the setup wizard
  (`electron-app/handlers/setupHandlers.ts:221`) deactivates any currency
  not selected during setup, and reaches EUR under conditions present in a
  full-suite run but not isolation (confirmed by querying both accumulated
  worker DBs directly). It deliberately leaves EUR active afterward (never
  deactivates it back) — grepped, no other spec anywhere asserts EUR is
  absent/inactive or asserts a currency-list count, so this is safe.
- `lira-146-exchange-cross-currency-override` is the SECOND spec to touch
  EUR (grepped — 143/144/145 don't), and the FIRST to write off a position
  via the admin `exchangeLots.adjust` negative-qty path. Before opening its
  own lot it queries `exchangeLots.getPositions()` for EUR and, if nonzero,
  writes off whatever lira-142 left open (the 217 EUR lot documented above)
  — otherwise FIFO would consume that lot first and every cost-basis/
  realized-profit assertion in this file would be silently wrong. This is
  safe for lira-142 itself (it already ran and made its own assertions
  before this file exists in the run order) and for every spec after this
  one: unlike lira-142, this file fully sells its OWN lot back down to ~0
  before it ends, so a FUTURE EUR-touching spec inherits an EMPTY position,
  not a 217 EUR (or any other) leftover — a cleaner terminal state than
  lira-142's. It also calls `rates:set` for EUR and LBP (idempotent —
  grepped, no other spec anywhere mutates either rate row, so this should
  be a no-op against create_db.sql's own defaults every time, not a
  correction) — a FUTURE spec that assumes the LBP/EUR rate row is
  UNTOUCHED-BY-ANY-SPEC should instead assume it is at these exact
  known-good values, which is what this file (and lira-096, read-only)
  already depend on.
- `lira-129-loto-refund` is the FIRST spec to ever call `loto.checkpoint.create` —
  `LotoService.createCheckpoint` sweeps **every** currently-uncheckpointed, non-refunded
  ticket and every unassigned cash prize **tenant-wide, with no date filter**. By the time
  it runs, it retires every stray uncheckpointed ticket earlier loto specs left behind
  (e.g. lira-092's unvoided `L092-VOIDBTN-…`) and every unassigned cash prize
  (lira-091-loto-ledger-sign's two) into its own checkpoint(s). This is safe for
  lira-129 itself (every assertion there is a delta taken around its own
  checkpoint-create/refund/settle, never an absolute total or balance) and it settles
  BOTH checkpoints it creates before the file ends — no `loto_checkpoints` row is left
  unsettled. Any FUTURE spec that assumes a ticket is still uncheckpointed after
  lira-129 has run (alphabetically before it: none currently do) would need its own
  fresh, unique ticket rather than relying on a stray from an earlier file.

- `lira-144-inventory-filters` leaves three products behind (`L144 Widget A/B/C`)
  carrying two categories and two suppliers (`L144CatA/B`, `L144SupX/Y`) that
  no other spec uses. They are permanent additions to the catalogue and to
  whatever `inventory:get-product-filter-options` returns from that point on.
  Safe today — grepped, and nothing in the suite asserts an absolute product
  count or an exact category/supplier option list (every category-touching
  spec — 060, 089, 093, 110, 123, 125, 132, 143 — sorts BEFORE it and matches
  by identity anyway). A FUTURE spec that wants "the number of products" or
  "the full options list" must account for them, or scope itself the way
  lira-144 does (a name/category prefix unique to the file).

- `lira-145-carrier-line-usage-expense` leaves THREE extra active `mtc`
  `carrier_lines` behind (labels `L145-A/B/C-<timestamp>`), each with a
  run-unique phone. Two end at their seeded credits (test (b) voids its usage,
  test (c) never commits one); test (a)'s line ends $12.50 down. Two knock-on
  effects to know about:
  (1) `carrierLines.create` never syncs the provider drawer (documented in
  `CarrierLinesPanel.tsx` and in lira-133's `seedPrimaryMtcLine`), so these
  seeds widen the pre-existing `drawer_balances["MTC"].USD` vs
  `getCarrierCreditsSum("mtc")` gap. Every assertion in this file is therefore
  a DELTA on both halves rather than the absolute §0.1 equality — a FUTURE
  spec that wants to assert that equality outright must reconcile the drawer
  first, not assume a clean start.
  (2) `getActiveByCarrier("mtc")` returns more rows from here on, so the
  Recharge MTC panel renders several line chips. Nothing asserts a line COUNT
  today (grepped: 125/132/133 all match by id or phone), and lira-145 itself
  scopes every locator to its own `carrier-line-<id>` marker. It deliberately
  does NOT call `setPrimary` — the primary MTC line stays whoever lira-133
  left it.
  Alphabetically only the unnumbered `lira-*` files and `recharge.spec.ts` run
  after it; all of them assert MTC drawer/credits by delta.

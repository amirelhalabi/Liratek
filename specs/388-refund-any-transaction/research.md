# Research: Refund any transaction (LIRA-388)

All findings verified against the code on 2026-11-11 (file:line in the build notes of tasks.md where it matters).

## R1. Where the refund decision lives

- **Decision**: a new leaf module `packages/core/src/constants/refundKinds.ts` exports `REFUND_OWNERS` (type → owner + kind + direction), `NON_REFUNDABLE_TRANSACTION_TYPES` (derived: `NON_REVERSIBLE_TRANSACTION_TYPES` minus the owned types), and `refundPlanOf(row)` (row-level: reversal rows, carrier-line edits without stored values). Both the service dispatcher and the Transactions page read it.
- **Rationale**: rule 14 — the page's hand-kept `ACTIONABLE_TYPES` becomes derived. Leaf module because the page imports it through `browser.ts` (rule 29).
- **Alternatives**: shrinking `NON_REVERSIBLE_TRANSACTION_TYPES` in place — rejected: ~20 consumers (posting rules, profit, migrations, CashFlowBadge) read it with the meaning "the generic path cannot reverse this", and the raw `transactions:void` must keep refusing a hold, voucher or legacy top-up.

## R2. One entry point

- **Decision**: the existing `transactions:refund` channel / `POST /api/transactions/:id/refund` (same schema, already in `channelPolicy` as `offline` with a binding) is the one entry. `TransactionService.refundTransaction` dispatches: `generic` → repository refund with `allowOwnedRefund`; `holdPickup` → `HoldMoneyService.voidPickup(pickupId)`; `voucher` → `VoucherService.cancelVoucher(source_id, {payments})`; `warranty` → `WarrantyService.voidClaim({claim_id: source_id}, actor)`; `none` → refusal with the reason.
- **Rationale**: no new channel means no new preload binding, adapter function, offline fixture or schema (rule 23 satisfied trivially); one place to route.
- **Alternatives**: a new `transactions:refund-any` channel — rejected as duplicate plumbing for the same payload.

## R3. Same-method confirm vs. today's Void

- **Decision**: the untouched window sends no `refundLegs` → `_reversePayments` mirrors every customer leg (same drawer, currency, amount) exactly as void does; module owners (`_cancelDebt`, `_markSourceRefunded`, partner/supplier/loto/carrier steps) are shared by both paths. Result: REFUND row (spec story 1) + identical money. Differences, documented and pinned by a comparison test: (a) profit reverses on the refund's day instead of the original vanishing from its day — identical for a same-day refund; (b) a back-timed row's checkpoint-resolution offset leg is not mirrored and `resyncShortageAfterVoid` does not run (the existing refund rule from LIRA-335).
- **Alternatives**: routing an untouched confirm to `voidTransaction` — rejected: conflicts with story 1 / FR-005 ("REFUND row linked, original REFUNDED") and would give a cashier two different outcomes for the same click depending on whether they touched the method.

## R5. "Reversed" signal on the page

- **Decision**: `getRecent`'s `reversed_by_id` (today: a REFUND row with `reverses_id = t.id`) widens through one SQL fragment to the page-owned reversal rows: HOLD_MONEY_COLLECT_VOID, WARRANTY_COST and COUNTERPARTY_DISCOUNT rows with `reverses_id = t.id`, and for a VOUCHER_SALE the VOUCHER_CANCEL of the same voucher (no `reverses_id` is written there; adding one would flip CashFlowBadge's sign logic). A cancelled hold drop-off is a generic REFUND, already covered.

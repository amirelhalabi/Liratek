## The spec of record

acceptance criteria, and technical traps. It is the canonical spec — this handover does NOT
duplicate it; read it first, then come back for the build guidance below.

Headline shape: ONE product per model (stock N, shared cost/price) + a per-unit IMEI table
(IN_STOCK/SOLD, sale_item link); IMEI joins search everywhere barcode works; `warranty_months`
on the product → warranty-until stamped on the sale line at checkout; unit pick REQUIRED at sale
for flagged products; refund flips the unit straight back to IN_STOCK plus a phone-specific
refund UI (`is_defective` flag + operator-settable new warranty expiry); gating = a boolean on
`product_categories`, seeded ON for the seeded "Phones" category.

## Traps specific to THIS build (the part worth reading twice)

- **`sale_items.imei` must keep being written** (receipts, SaleDetailModal, old readers parse
  it) while the units table owns state — one owner of "which unit sold" (§13 item 14): the
  unit row is truth, `sale_items.imei` is a projection stamped at sale time.
- **Cart.tsx:101** — the existing IMEI input renders on `category.toLowerCase().includes("phone")`:
  "Headphones" false-positives TODAY. Replace the gate with the category flag; don't stack on it.
- **Refunds live in the Transactions page only** (owner decision 2026-07-04) — the phone refund
  UI extras belong in THAT flow, not a POS surface.
- **Sales can sit in session baskets** (§13 item 11): the unit pick must survive the verbatim
  `formData` replay at checkout (lira-094 pattern — the page's session branch must put the
  chosen unit into formData). Sweep the session branch or document the exclusion explicitly.
- **Seeded-category backfill is name-matched** — a tenant who renamed "Phones" gets no
  auto-flag; that's accepted (Settings toggle), say so in the migration comment.
- **E2E shared-DB discipline**: self-provision everything (a flagged category, a product with
  units) — the setup wizard runs early in the suite and mutates config (it deactivates
  non-selected currencies; assume it can touch anything). Distinctive amounts as identity.
  lira-142's `ensureEurActive()` is the provisioning template. Desktop e2e BEFORE web (ABI).
- **Decision #12 has a named answer-during-build question** (does a refund warranty-override
  prefill the unit's next sale? default: no, fresh stamp wins, override cleared) — decide it
  consciously during phase 4 and record the answer in the ticket.

## Environment quirks (all hit this session; all have workarounds)

- Agent shell: `yarn dev`/`yarn test:e2e` no-op silently — decompose (`yarn rebuild:native` +
  `yarn workspace @liratek/electron-app build`) and run Playwright directly from `frontend/`:
  `env -u ELECTRON_RUN_AS_NODE npx playwright test --config playwright.electron.config.ts`.
- ABI dance: jest needs Node ABI, desktop e2e needs Electron ABI; `yarn test` self-corrects;
  if the owner's app holds the binary, use a scratchpad-installed better-sqlite3 via a scratch
  jest `moduleNameMapper` (proven twice this session).
- `cmd /c` from Bash is broken; use yarn/npm/node directly. Big `tsc` runs may need
  `NODE_OPTIONS=--max-old-space-size=4096`.
- Disk: e2e leaks ~35MB profiles per worker per run into `%TEMP%\liratek-e2e-*` — the owner is
  storage-constrained; clean these after e2e sessions (safe, documented leak).
- The playwright tsconfig typecheck (`npx tsc -p tsconfig.playwright.json --noEmit` from
  frontend/) is NOT covered by `yarn typecheck` — run it for spec changes; it's at 0 errors.
